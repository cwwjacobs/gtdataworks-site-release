Prototypes turned into services that stay up.

What it is

You have a model or agent that works on a laptop, in a notebook or on a single box, and it now has to serve real users without someone watching it. GTDataWorks containerizes it, puts it behind CI/CD with secrets management, and deploys it to Modal, Google Cloud Run, Hugging Face or your own Docker hosts. Where an agent executes tools or code, it can run inside a default-deny microVM sandbox, so a bad instruction cannot reach anything it was not meant to.

Your users should notice nothing, which is the point: the service answers at the same address every day, releases roll out without taking it down, and when something breaks an alert reaches you before a customer does. You keep the accounts, the keys and the repository. The studio works inside them, and its access ends at handover.

What you get

Every item lands in your repository and your hosting account, not the studio's. The runbook is written for whoever will be on call, and the handover call walks them through it.

How the work runs

  1. Containerize

    A Dockerfile and Compose file for the service as it exists today: pinned dependencies, a health endpoint, configuration through environment variables. The same image runs on your laptop and on the host.

  2. CI/CD

    A GitHub Actions pipeline that builds the image, runs your tests and deploys a tagged release to Modal, Google Cloud Run, Hugging Face or your Docker host. Rolling back is redeploying the previous tag.

  3. Secrets and sandboxing

    Provider keys move out of the repository and into the host's secrets store, one scoped key per provider. Agent workloads that run tools or code go into a gVisor or Firecracker sandbox (cindermote) with a default-deny network policy, so the agent can reach only the hosts on its allow-list.

  4. Monitoring

    Prometheus metrics and Grafana dashboards for latency, error rate, throughput and spend, with alert rules for the failures the runbook anticipates, routed to your email or Slack.

  5. Runbook and handover

    A runbook that covers deploy, rollback, key rotation and the likeliest failures, then a handover call with whoever will be on call. The studio's access is removed at the end unless you ask for ongoing hourly support.

Where it fits

A good fit when

  • A prototype works and there is a repository the studio can build from.
  • You want to own the infrastructure: your Modal, Google Cloud or Hugging Face account, or your own Docker hosts.
  • The agent runs tools or code and needs isolation from the rest of your network.

Not a fit when

  • There is no prototype yet. Start with AI Consulting & Proof-of-Concept, or have the agent built under Conversational AI & RAG Agents.
  • You need AWS, Azure, SageMaker or Kubernetes delivery. GTDataWorks deploys to Modal, Google Cloud Run, Hugging Face and Docker hosts, and does not take on stacks it has not shipped.
  • You would rather not run anything yourself. For MCP servers there is a hosted option: Managed MCP Servers.

Questions

Where does the service run, and whose account is it?

Yours. Modal, Google Cloud Run, Hugging Face and Docker hosts are set up under accounts you own and pay for directly; GTDataWorks is added as a collaborator for the length of the engagement. Your production traffic never passes through a GTDataWorks system.

Who holds the API keys?

You do. Keys for OpenAI, Anthropic and any other provider are created in your provider accounts and stored in the host's secrets manager, never in the repository or in a chat thread. Bring the keys you already have; the deployment reads them from the secrets store at runtime.

What does the monitoring cover?

The service: latency, error rate, throughput, spend and the host's own health, as Prometheus metrics on Grafana dashboards with alert rules. What the bot said and how often it was right is a different question, answered by Monitoring & Analytics for AI Systems.

What happens after handover?

The pipeline, dashboards and runbook work without the studio, and most teams run on their own from there. If you want changes later, the work is billed at the hourly rate on this page, and the runbook, config and pipeline history from the original engagement are the starting point.
