The CRM write, the booking, the notification and the receipt are the two-week build. The live brief builder stops after the conversation: it assembles the brief for you to send, with no backend and no model call.

Purpose

Automate the first contact without hiding anything from the person on the other end. The agent asks what you are trying to build, collects budget band, timeline and contact details, answers the usual pre-sales questions from a fixed set of studio facts, and books a follow-up call. Today the form of record is the brief builder on the contact page: a static, no-backend version of the same flow that composes the brief for you to send.

Core features

  • Conversational form-filling: name, company, project type, budget band, timeline, contact details
  • Pre-chat FAQ answered only from the published catalog: prices, timelines, what ships
  • Lead scoring against the catalog: service fit, budget band, urgency
  • Lead created in HubSpot or Salesforce through the REST API, with the brief attached
  • Receipt per session: what was asked, what was answered, what was written to the CRM, and when

Integrations

HubSpot or Salesforce REST API to create the lead. n8n or Zapier to send the confirmation email. Google Calendar API to book the follow-up call. Hosted on Modal or Google Cloud Run, with the model behind the OpenAI or Anthropic API.

Purpose

Show retrieval-augmented generation working the way a client build would. The question goes to an index, the top passages come back with scores, the model answers from those passages and nothing else, and the reply lists its sources. A visitor can inspect the whole chain instead of taking the answer on trust. The public corpus is a small fixture of sample documents, not client data.

Core features

  • Question answering over a document corpus with embeddings and top-k retrieval
  • A citation on every claim: document, section and retrieval score
  • Summaries of long documents on request
  • A basic chart from retrieved tables on request
  • Receipt per query: question, document ids and scores, model and prompt version, response hash

Integrations

Embedded on the site as a React widget. Session logs go to a Postgres table for the metrics in the sidebar. Optionally the GitHub API, so the same agent can answer questions about a public repository as a technical demo.

Lead Qualification Voice/SMS Agent

Calls or texts a new inbound lead, delivers a short approved pitch, asks the qualifying questions and books a demo when the answers fit.

Every outbound call or text passes a policy check first, and every contact ends in a receipt whether or not the lead qualifies.

Purpose

For B2B clients with more inbound leads than hours to call them. The agent reaches each new lead within minutes over Twilio, by voice with SMS as the fallback, follows a script you approve, records the answers, and either books a demo or hands the lead back with notes. Consent and opt-out are handled at the start of every contact and written to the receipt. This is the hardest of the four to build: voice adds latency, interruptions and transcription quality to the test plan, which is why the estimate is four weeks.

Core features

  • Outbound calls through Twilio Voice, with speech recognition and synthesis on the call; SMS conversation when the call is not answered
  • Pitch and qualifying questions approved by you and versioned, so a change in the script shows up in the receipts
  • Opt-out honoured on the first ask and recorded
  • Demo booked through the Google Calendar API, invite sent to the lead
  • CRM updated with the outcome, the answers and the receipt id

Integrations

HubSpot or Salesforce REST API for the lead record and the write-back. Twilio Voice and Messaging. Google Calendar API for the booking, with a Zoom link as an option. Orchestrated in Node.js with a Python backend; each outbound action is gated by a policy check and logged as a JSONL receipt, the Terminus Gate Protocol pattern.

Answers questions about internal documents and code, scoped to what the person asking is allowed to read.

Ingestion runs separately: a scheduled script embeds documents, wiki pages and repositories into the index and labels each chunk with its source and access group.

Purpose

Built for the studio's own use first: find the LangChain example from a past project, summarize the SOP on agent security, list which repositories use a given library. It is not client-facing, but it is the same pattern as a client's internal knowledge agent, and it is where the access-control and logging work gets proven before it ships to anyone else.

Core features

  • Retrieval over documents, wiki pages and repositories, with per-source access labels
  • Access check on every question: read-only, scoped by OAuth to the sources the asker may see
  • Answers cite file and section, and say “not in the sources” rather than guess
  • Exposed as an MCP server, so Claude, ChatGPT or any MCP client can use it as a tool
  • Receipt per question: who asked, which sources were searched, which were returned

Integrations

Slack or a command-line client for questions. GitHub for repositories. A scheduled ingestion script that records what it indexed and when. Served as an MCP server on Modal or Google Cloud Run.
